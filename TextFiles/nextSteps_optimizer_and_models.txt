B) Concrete optimiser improvements (highest impact first)

1) Make “strict vs relaxed” a controlled ablation (thesis-quality)
 - Add a third demo run: soft laycan end with a cap (`max_late_days`, e.g. 1–3 days).
 - Sweep `late_penalty_scale` (e.g. 1e-4, 1e-3, 1e-2) and record a tiny table:
   - served count, laycan violations, and overlap with manual vessel assignment.
 - Outcome: Chapter 4/5 can justify the chosen policy and show trade-offs.

2) Penalise excessive vessel usage (realism knob)
 - Add an optional “start-vessel penalty” term:
   - A binary variable per vessel that activates if any arc leaves `O_v`.
   - Add `vessel_used_penalty * used_v` to the objective.
 - This lets you avoid solutions that use many vessels for marginal gains, and it’s easy to justify in text:
   - “We add a fixed cost per activated vessel to reflect operational overhead / chartering friction.”

3) Unify parsing/semantics across runners (reduce confusion)
 - `Models/run_optimizer_sample.py` currently parses dates with a fixed format (`%d-%b-%y`) while the thesis demo uses `format="mixed"`.
 - Align date parsing and laycan derivation so “baseline experiments” are comparable and reproducible.

4) Add a small feasibility-focused arc pruning rule (speed + stability)
 - When generating arcs, prune arcs that cannot possibly meet laycan start by a wide margin.
 - Add a transparent threshold (e.g. if earliest-arrival > laycan_end + window_slack_days, drop arc).
 - This improves solve time and reduces degenerate solutions on larger instances.

5) Add a minimal “waiting” realism note (documentation)
 - The current model implicitly allows waiting (because the solver chooses `t_j` within the time window).
 - In Chapter 4, explicitly state: “waiting is allowed and does not incur explicit cost beyond time-weighted repositioning.”
 - Optional: add a small waiting penalty term if needed for realism.
