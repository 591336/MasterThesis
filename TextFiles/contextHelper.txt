 - Numerical features: vessel dimensions (DWT_SUMMER, DRAFT_SUMMER, LOA, BEAM), DAYS_STOPPAGES, DAYS_EXTRA_IN_PORT.
 - Derived signals: seasonal dummies, interactions (e.g., PORT × IS_BALLAST), log-transform of DAYS_IN_PORT for variance control (track inverse transform).

Optimizer integration context (frontend/data plumbing) – 2025-12-04
 - Scenario selection flow: `getScenarioSelector` typeahead queries `TSModelType.scenario` with fields {scenarioCode, scenarioName, isBudget, fleetPlan{code,name}, budgetVersion.name}; filters by isBudget and ignores budget scenarios for fleet plans. Selected scenario stored in selectedTSModel slice and feeds `getFleetPlansData`.
 - Loader orchestration: `ScenarioActions` reacts to selectedScenario changes; per-tab loaders fire (Open Positions, Scheduler, Cargo Mgmt, Voyages, Cargoes) plus `scenarioActions.loadFleetPlanData` for vessels. Filters always include scenario.key and date window from `FLEET_PLANS_DATE_FILTER_CODE`; MASTER adds vesselCodes.isSchedulable=true.
 - Data pulled per tab: vessels (FAS_SCENARIO_VESSELS_ID), unallocated voyages/commitments (FAS_SCENARIO_VOYAGES_ID) with tab-specific fields, allocated fleet plan voyages (FAS_FLEET_PLAN_VOYAGES_ID or comparing ID), vessel open positions (FAS_VESSEL_OPEN_POSITIONS_ID), unallocated cargos (FAS_SCENARIO_CARGOS_ID). Scheduler comparison loads a second scenario’s fleet plan voyages.
 - Actions available: create/allocate voyage (`FasFleetPlanVoyageApi.createAndAllocate`), move (`.move`), unallocate/remove (`.unallocate`, cargo allocate/copy). After changes, prefer targeted reloads (`ScenarioActions.reloadColumnData(grouping, source, target)` or tab-specific load* with vesselKeys) over full refresh.
 - Optimizer inputs to expect: scenario identity (key/code, fleetPlan.key; skip isBudget), active date window filters, current datasets (vessels, unallocated voyages, fleet plan voyages with sequence, open positions, cargos, optional compare scenario). Outputs should call voyage/cargo APIs and trigger targeted refreshes.
 - New scaffolds: 
    • `Models/optimizer.py` defines adapters for model access, `OptimizerRequest`/`OptimizerResult`, action types (allocate/move/unallocate), and a GreedyOptimizer placeholder that assigns unallocated voyages round-robin across vessels using column hints. Seeded randomness; logs note that constraints/model scores are not yet applied.
    • `Models/optimizer_mip.py` adds an arc-based MIP prototype (pulp/CBC). It builds vessel-specific start/end dummies, binary arc vars, start-time vars, unserved penalties, and early/late slack on time windows. Turnaround times come from the adapter; sailing times now call the sailing-time adapter (fallback uses `MILES_DIRECT/12 kn`). Vessel availability timestamps and voyage laycans (from cargo when present) set time-window bounds; big-M derives from the scenario window. Outputs allocate actions from the selected arcs; falls back to greedy if no incumbent.
    • `Models/run_optimizer_sample.py` runs sample experiments on the Stena sample data; proxy predictors used (sailing from `MILES_DIRECT`, turnaround=1d). Experiments tried: baseline (65 vessels/324 voyages, penalty 1000, arcs/job=5) → 65 single-leg allocations; tuned low penalty (penalty 100, arcs/job=10, 60s) → 65 single-leg allocations; subset (10 vessels/30 voyages) → still single-leg. Chaining not observed yet—arc feasibility + missing availability and economic incentives keep solutions at one leg per vessel. Date parsing warnings persist until date formats are explicitly set.
