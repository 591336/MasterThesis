FuelEU Maritime – Regulatory Context (authoritative, 2025)
 - Scope: Ships > 5,000 GT on voyages calling EU ports, in force from 2025, covers CO2/CH4/N2O, Well-to-Wake. GHG intensity targets: -2% in 2025 ramping to -80% by 2050. Compliance via financial penalties.
 - Key fuel inputs: LCV (MJ/g), EF_WtT (gCO2e/MJ), EF_TtW (gCO2e/MJ). Energy accounting uses EU ETS-adjusted fuel consumption (m_fuel).
 - Core variables: m_fuel (tonnes), LCV, EF_WtT, EF_TtW, E_total (MJ), GHG_intensity (gCO2e/MJ), GHG_limit, Compliance Balance (CB), Penalty_price (EUR/t CO2e).
 - GHG intensity calc: E_total = m_fuel * LCV * 1e6; WtT = E_total * EF_WtT; TtW = m_fuel * EF_TtW * 1e6; GHG_intensity = (WtT+TtW)/E_total.
 - Compliance balance: CB_raw = (GHG_limit − GHG_intensity) * E_total; CB_CO2 = CB_raw / ((GHG_intensity/1e6)*41,000). Penalty applies if CB_CO2 < 0: Penalty = |CB_CO2| * Penalty_price.
 - Implementation notes: calculate per fuel then aggregate; GHG limits depend on voyage start year; penalties reported in voyage P&L. Optimizer objective can trade fuel mix/routing vs penalties; use P50/P80 buffers for uncertainty.

Restricted Areas – Regulatory Context (authoritative)
 - Purpose: Geographic zones with special environmental/operational rules that constrain fuel categories, engine usage, scrubber requirements, and open-loop permissions.
 - Core fields: code, name, start_date, end_date (nullable), open_loop_restricted (bool), geojson boundary. Area is active if start_date ≤ voyage_date ≤ end_date (or end_date null).
 - Fuel allowance: A bunker category is legal only if explicitly allowed for the engine type; if open_loop_restricted=true, then bunker.open_loop_allowed must be false; if scrubber_required=true, vessel must have scrubber. Treat missing/undefined permissions as disallowed.
 - Priority: Each allowed fuel has a priority (lower = preferred) per area; used as a secondary objective after legality/cost.
 - Optimisation implications: route → applicable areas; applicable areas → legal fuels per leg; overlapping areas must all be satisfied. Objective order: compliance (hard), availability/capability, cost, priority.
 - Data governance: restricted area data treated read-only for optimisation; only superusers may create/delete areas, edit boundaries, open-loop flags, priorities, or allowed fuel lists.
 - Implementation notes: evaluate at leg level; cache spatial intersections; ignore expired areas; enforce legality first, then apply priority/cost.

Thesis-ready vs Business-ready (Optimizer)

Thesis-ready scope (what we aim to “finish” now)
 - Goal: a reproducible optimiser prototype that produces physically consistent schedules/actions on the Stena sample scenario and supports thesis evaluation/figures.
 - What must be true (“good enough” gates):
   * No per-vessel time overlaps in exported schedules: overlaps=0 in `Visualizations/output/eval_*.txt`.
   * No missing timestamps in exported schedules: missing_times=0.
   * For strict-feasibility runs (`hard_laycan_end=True`): laycan start violations=0 and laycan end violations=0.
   * Demonstrate trade-off: show both a coverage-first run and a strict-feasibility run on the same dataset (e.g. `manual_match` vs `manual_match_physical`) with evaluator outputs saved.
   * Reproducibility: single-command run instructions in `TextFiles/runGuide.txt` and deterministic outputs committed/archived for thesis reference.
 - Deliverables to lock for the thesis:
   * Scripts: `Models/run_optimizer_sample.py`, `Models/evaluate_optimizer_output.py`, `Visualizations/gantt_viz.py`.
   * Thesis bundle runner: `Models/run_thesis_optimizer_demo.py` (generates both strict and coverage-first artefacts with stable filenames).
   * Artefacts: `Visualizations/output/allocations_*.csv`, `schedule_*.csv`, `eval_*.txt`, `gantt_sample.png`.
   * Narrative: short write-up of constraints/objective/assumptions + evaluation metrics (served count, violations, runtime).
 - Thesis automation: `Models/run_thesis_optimizer_demo.py --require-gates` exits non-zero if the strict run violates the feasibility gates above.

Business-ready scope (explicitly out of scope for thesis MVP)
 - Real integration: wiring optimiser outputs into the frontend/API workflow (create/move/unallocate + targeted refresh), permissions, audit logging, retries, and user-facing explanations.
 - Full constraint set: cargo/vessel compatibility, draft/beam restrictions, contractual priorities, open positions, port restrictions, prohibited sequences, multiple resources, and richer availability handling.
 - Performance guarantees: predictable runtime at production scale (hundreds/thousands of voyages) via stronger pruning, decomposition, warm starts, solver configuration, and fallbacks.
 - Robust QA: automated tests, regression datasets, CI gating, monitoring/telemetry, and clear failure modes.

Laycan policy note (thesis MVP)
 - We support two laycan-end policies in the MIP:
   * Hard laycan end (`hard_laycan_end=True`): start time must be ≤ laycan end when the field is present; infeasible voyages remain unserved.
   * Soft laycan end (`hard_laycan_end=False`): allow starting after laycan end with a lateness slack and penalty; optionally cap lateness via `max_late_days`.
 - The sample exports include `ESTIMATED_VOYAGE_START_DATE` in the manual plan, but it is not guaranteed to match cargo laycans one-to-one (and laycans are missing for many sample voyages), so we keep the policy as an explicit toggle for thesis runs rather than trying to infer a single “correct” semantics from the sample.
