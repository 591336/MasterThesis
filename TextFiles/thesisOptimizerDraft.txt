Optimizer prototype (thesis draft text)
=====================================

This section documents the current “thesis-ready” optimiser prototype used for the Stena sample scenario. The goal is not a production-grade scheduling system, but a reproducible allocation prototype that produces physically consistent vessel timelines and generates auditable artefacts (CSV schedules + evaluation reports + Gantt figures) that can be referenced in the thesis.

Problem statement
-----------------
Given a set of vessels and a set of candidate voyages to be performed in a planning window, produce an allocation (a sequence of voyages for each vessel) that:
1) is physically feasible in time (no overlapping voyages on the same vessel),
2) respects (or intentionally relaxes, with penalties) voyage time-window constraints (“laycans”),
3) optionally prefers keeping voyages on the same vessel as an existing manual plan, and
4) trades off serving more voyages vs. leaving infeasible voyages unserved.

Data inputs (sample scenario)
----------------------------
The prototype operates on the exported Stena sample scenario files:
- Vessels: `DataSets/Derived/Stena/SampleScenario/vessels_with_availability.csv`
  * Includes vessel identifiers and an initial availability timestamp (`VESSEL_AVAILABLE_UTC`) plus an “open port” (`VESSEL_OPEN_PORT_ID`) when present.
- Candidate voyages: `DataSets/Derived/Stena/SampleScenario/unallocated_voyages_detailed.csv`
  * Includes origin/destination ports, distance fields, economics fields, and laycan window columns (`LAYCAN_START_UTC`, `LAYCAN_END_UTC`) where available.
- Manual plan (for evaluation only): `DataSets/Derived/Stena/SampleScenario/fleet_plan_manual.csv`
  * Contains vessel-voyage sequences for the manual plan; used to compute overlap metrics, not as a hard constraint.

Models and methods used (what and why)
--------------------------------------
The thesis prototype combines (a) predictive models for travel/service time estimation and (b) a constrained optimiser for sequencing and assignment. The key design intent is that the optimiser consumes time estimates through a narrow adapter interface, so modelling choices can be swapped without rewriting the optimiser.

Predictive models (time estimation)
1) Sailing-time model (ML)
- Target: `HOURS_PER_NM` (hours per nautical mile).
- Training pipeline: scikit-learn `Pipeline` with:
  * preprocessing: imputation + one-hot encoding of categorical fields + numeric median imputation,
  * estimator: `DecisionTreeRegressor` (baseline, interpretable).
- Training data and guardrails:
  * Dataset builder: `Models/build_sailing_time_dataset.py` (filters implausible values by keeping `HOURS_PER_NM` in [0.02, 5.0]).
  * Chronological splits + feature manifest: `Models/train_sailing_time_model.py`.
  * Training + report: `Models/fit_sailing_time_model.py` (reports MAE/RMSE/sMAPE against a median baseline).
- Features (high-level):
  * Categorical: vessel type, canal passage flag, month/season, plus derived keys (e.g. vessel_type×month).
  * Numeric: distance measures, ballast fraction, days-at-sea, basic vessel dimensions, cargo aggregates, canal cost, vessel age.
- Why this target/estimator:
  * `HOURS_PER_NM` normalises for distance and yields a stable quantity that can be multiplied by voyage miles to get travel time.
  * A decision tree baseline is easy to explain in the thesis, fast to train, and robust to nonlinear interactions without heavy tuning.
- Artefact used by the optimiser demo: `Models/Artifacts/stena/sailing_time_dt.joblib` (loaded via `Models/optimizer_adapters.py`).

2) Port turnaround model (ML)
- Target: `DAYS_IN_PORT` (turnaround duration in days).
- Training pipeline: same pattern as above with a scikit-learn `Pipeline` and `DecisionTreeRegressor`.
- Training data and guardrails:
  * Dataset builder: `Models/build_port_turnaround_dataset.py` (filters implausible values by keeping `DAYS_IN_PORT` in [0.04, 10]).
  * Chronological splits + feature manifest: `Models/train_port_turnaround_model.py`.
  * Training + report: `Models/fit_port_turnaround_model.py` (reports MAE/RMSE/sMAPE against a median baseline).
- Features (high-level):
  * Categorical: port/terminal identifiers (when available), ballast flag, vessel type, month/season, commodity grouping (when available), and derived keys (e.g. port×ballast).
  * Numeric: vessel dimensions and stoppage durations (where available).
- Why ML rather than a single global average:
  * Port turnaround depends on port, terminal availability, ballast vs loaded patterns, vessel type, and seasonal effects; even a simple model can capture some structure.
- Artefact used by the optimiser demo: `Models/Artifacts/stena/port_turnaround_dt.joblib`.

Model adapters (bridge between data and optimiser)
- The optimiser does not call scikit-learn directly. Instead it uses adapter classes that:
  * map/derive the expected model features from the optimiser’s input rows,
  * handle missing columns robustly,
  * convert model outputs into the optimiser’s required units (days).
- Concretely, the demo uses:
  * `Models/optimizer_adapters.SailingTimeModelAdapter` (converts `HOURS_PER_NM` → sailing days),
  * `Models/optimizer_adapters.TurnaroundModelAdapter` (predicts turnaround days).

Baselines and alternatives (explicit options)
- Lookup-table baselines exist in this repository (medians by key hierarchy) for both sailing time and port turnaround.
  * These are useful in a thesis as “simple, explainable baselines” and as robust fallbacks.
- Alternative ML estimators are supported in training scripts (e.g. histogram gradient boosting), but the thesis demo uses a decision tree for simplicity and interpretability.
- The optimiser itself could also be implemented using:
  * greedy heuristics / local search (fast but harder to guarantee feasibility without careful engineering),
  * constraint programming (strong for scheduling), or
  * other MIP solvers (commercial or open-source).
  For the thesis prototype, PuLP/CBC is sufficient to demonstrate the modelling approach and to produce reproducible results on the sample scenario.

Ablations and design options (what changes and expected impact)
--------------------------------------------------------------
This subsection lists the main “knobs” in the prototype, what they change, and what effect we expect on the evaluation metrics. The purpose is to make modelling/optimisation choices explicit in the thesis and to justify why the selected configuration is used for the thesis demo.

Time estimation options (models → schedule physics)
1) Sailing time model
- Option A (used in thesis demo): ML `HOURS_PER_NM` → sailing days via `days = hours_per_nm * miles / 24`.
  * Expected impact: better differentiation across vessels/conditions than a constant speed; improves plausibility of time propagation and sequencing.
- Option B (baseline): lookup medians by key hierarchy (e.g. vessel type × canal × month), then apply the same conversion to days.
  * Expected impact: more stable/robust in sparse regimes; may underfit operational variability but often improves generalisation versus a weak ML model.
- Option C (fallback heuristic): constant speed (e.g. 12 kn) with haversine/direct miles.
  * Expected impact: fastest and most explainable, but may distort feasibility (too fast/slow) and change which arcs appear feasible.

2) Turnaround (service time) model
- Option A (used in thesis demo): ML turnaround days (port turnaround model).
  * Expected impact: introduces port/vessel heterogeneity; reduces “unrealistically dense” schedules where many voyages fit back-to-back.
- Option B (baseline): lookup medians by port/terminal/ballast/month hierarchy.
  * Expected impact: strong explainability; robust when ML is noisy; similar scheduling effect to ML if the lookup is well-covered.
- Option C (fallback heuristic): constant turnaround (e.g. 1 day).
  * Expected impact: can materially inflate feasibility and increase served count artificially; useful only as a debugging baseline.

Laycan semantics options (feasibility vs coverage trade-off)
1) Hard laycan end (`--laycan-end hard` / `hard_laycan_end=True`)
- Meaning: voyage start must occur within the laycan end bound when present.
- Expected impact on metrics:
  * Served voyages: decreases (some voyages become infeasible).
  * Laycan end violations: forced to 0 by construction.
  * Interpretability: strongest “physically realistic” claim for the thesis.

2) Soft laycan end (`--laycan-end soft`, lateness slack + penalty)
- Meaning: allow starting after laycan end with a nonnegative lateness slack and penalty in the objective.
- Expected impact on metrics:
  * Served voyages: increases.
  * Laycan end violations: increases unless penalties are strong enough to discourage lateness.
  * Use in thesis: best for demonstrating why semantics matter and why “served count” alone is misleading.

3) Soft + lateness cap (`--max-late-days X`)
- Meaning: allow lateness but limit it to X days, enforcing “bounded realism”.
- Expected impact: middle ground between hard and soft; useful when laycan end is “preferred” rather than “hard” in the domain interpretation.

Arc generation and pruning options (runtime vs solution quality)
The arc set controls both solve time and solution quality: too many arcs leads to slow solves; too few can remove the true best sequence.

Key parameters:
- `max_arcs_per_job` (K): number of outgoing job-job arcs retained per voyage.
  * Higher K: better solution space, slower solve; lower K: faster solve, higher risk of missing good sequences.
- `job_job_candidate_window` (W): forward window size in time order used to generate candidates before selecting the best K.
  * Higher W: gives pruning heuristic more choices (helps); too high increases arc set and runtime.
- `job_job_selection` method:
  * `time`: keep the next K voyages in time order.
    - Expected: good when laycans are dense and chronological ordering dominates feasibility; may ignore reposition distance.
  * `reposition`: choose K successors with smallest reposition duration within the window.
    - Expected: improves physical realism (reduces teleporting/long reposition jumps) and can improve solver stability by favouring plausible chains; may miss profitable long jumps.

Objective weight options (what the optimiser “prefers”)
These weights do not change feasibility, but they change which feasible plan is chosen.
- `unserved_penalty`: larger values push toward serving more voyages; too large risks pushing the model into late/implausible choices unless laycans are hard/capped.
- `late_penalty_scale` and `max_late_days`: control how much the optimiser is willing to violate laycan end in soft mode.
- `time_weight`: increases the cost of repositioning and thus encourages geographically plausible sequences.
- `switch_penalty` (manual preference): increases “stay on the same vessel as manual”; too high can force poor feasibility/coverage if the manual allocation conflicts with laycans/availability.

Solver/constraint options (correctness vs runtime)
- `time_limit_sec`: higher values generally improve solution quality but reduce reproducibility of run time; for thesis we prefer a fixed budget and report it.
- Disjunctive non-overlap constraints (`--enable-nonoverlap` in the sample runner):
  * Expected: can strengthen non-overlap guarantees in some formulations, but is expensive (quadratic in jobs) and not needed when time propagation + positive durations are enforced correctly.

Expected directional effects summary (metric-level)
- Tighten feasibility (hard laycan end, reduce allowed lateness): served ↓, violations ↓.
- Increase unserved penalty / soften laycans: served ↑, violations ↑ (unless capped/penalised strongly).
- Improve time estimates (better sailing/turnaround): feasibility becomes “more realistic”; served may go either direction depending on whether prior estimates were optimistic or pessimistic.
- Increase pruning (smaller K/W): runtime ↓, risk of suboptimal/fragile solutions ↑.

Predicted travel/service times
------------------------------
The optimiser needs time estimates to build a physically consistent schedule.

Sailing time:
- A trained sailing-time ML model predicts `HOURS_PER_NM`.
- For optimisation, this is converted to a sailing duration in days:
  `sailing_days = (hours_per_nm * miles_total) / 24`.
- In the sample, `miles_total` is taken from voyage fields (preferring total miles when available, otherwise direct miles; if missing, a haversine fallback may be used if port lat/lon is available).
- Practical note: the optimiser depends on unit consistency. The thesis version explicitly enforces a single contract: “sailing time passed to the optimiser is in days”.

Turnaround / service time:
- A trained port turnaround model predicts a turnaround duration in days.
- In the prototype, the “job duration” used in time propagation is:
  `duration_days(job) = sailing_days(job) + turnaround_days(job)`,
  clipped to be strictly positive (a small minimum is enforced) to prevent degenerate zero-duration cycles.
- Modelling simplification: turnaround is treated as a voyage-level service time. A more realistic model would treat load and discharge port calls separately; this is noted as future work.

Time-window (laycan) modelling
------------------------------
The prototype supports two explicit policies for the laycan end (`LAYCAN_END_UTC`) constraint:

1) Strict feasibility (“hard laycan end”)
- Interpretation: the voyage start time must satisfy `start_time <= laycan_end` when laycan end exists.
- Infeasible voyages remain unserved (the model can pay an “unserved penalty” instead of allocating).

2) Coverage-first (“soft laycan end”)
- Interpretation: `start_time` may exceed `laycan_end` via a nonnegative lateness slack variable.
- The objective penalises lateness so the solver can trade off “serve more voyages” vs. “serve on time”.
- This mode is used only as a contrast run to demonstrate the feasibility/coverage trade-off.

Because the exported manual plan does not reliably encode laycan semantics (and laycan fields are missing for many voyages), the thesis version keeps laycan policy as a deliberate toggle rather than trying to infer a single “correct” semantics from the sample export.

Optimisation model (MIP prototype)
---------------------------------
The prototype is formulated as an arc-based mixed-integer programme (MIP) solved with PuLP/CBC.

Decision variables:
- Binary arc variables `x[v, i, j]` indicating whether vessel `v` traverses arc `i -> j` (where nodes `i` and `j` are either voyages or vessel-specific dummy nodes).
- Continuous start-time variables `t[j]` for each voyage `j` (interpreted as the voyage start time).
- Binary unserved variables `y[j]` indicating whether voyage `j` is left unserved.
- Continuous late slack variables `late[j]` (only used in soft laycan end mode).

Core constraints:
- Each voyage is either served once or marked unserved:
  `sum_incoming_arcs_to_j x[*, *, j] + y[j] == 1`.
- Flow conservation per vessel and voyage (if a vessel visits a voyage, it must also leave it):
  `sum_incoming_arcs_for_(v, j) == sum_outgoing_arcs_for_(v, j)`.
- Degree constraints (prevents branching artefacts):
  `sum_incoming_arcs_for_(v, j) <= 1` and `sum_outgoing_arcs_for_(v, j) <= 1`.
- Time propagation (physical non-overlap):
  For each selected arc `i -> j` on vessel `v`,
  `t[j] >= time(i) + reposition(i->j) + duration(i)`.
  Here `time(i)` is either the vessel availability time for start arcs or `t[i]` for voyage nodes.
- Laycan bounds:
  `t[j] >= laycan_start` (when present).
  `t[j] <= laycan_end` (hard mode) OR `t[j] <= laycan_end + late[j]` (soft mode).

Arc generation and pruning:
- Start arcs connect each vessel’s dummy start node to each candidate voyage.
- Job-job arcs are pruned for performance:
  we consider only a forward “candidate window” of voyages in time order, and then select up to K successors per voyage.
- For thesis runs on the manual set, successors are selected using a reposition-distance heuristic (`job_job_selection = reposition`) within a forward candidate window (`job_job_candidate_window = 30`) and capped (`max_arcs_per_job = 6`).
- Why pruning is necessary:
  the number of possible job-job arcs grows quadratically with voyages. Pruning provides a controlled approximation that keeps run times predictable while still allowing multi-leg sequences.

Objective (high-level)
----------------------
The objective trades off three terms:
1) Unserved penalty: encourages serving voyages when feasible (and economically desirable).
2) Time/transition penalties: encourages shorter repositioning and discourages excessive slack.
3) Optional “manual preference”: a small penalty can be applied when a voyage is assigned to a different vessel than in the manual plan (soft preference, not a constraint).

For the thesis demo runs, the objective is mainly used to show the feasibility/coverage trade-off under two laycan policies; it is not claimed to represent the full business objective.

Objective implementation notes (prototype detail)
- Each arc has a “cost” used in the objective. In the current prototype this combines:
  * a scaled economic proxy (derived from voyage revenue/cost columns when present), and
  * a time-weighted term (e.g. reposition duration).
- The scaling (`cost_scale`) exists to keep objective magnitudes numerically stable relative to the unserved penalty and slack penalties.
- The thesis text should treat the economic term as a proxy (illustrative), not a calibrated profit model.

Reproducibility and artefacts
-----------------------------
The thesis demo is produced by a single command:

`uv run python Models/run_thesis_optimizer_demo.py --time-limit-sec 60 --output-prefix thesis --require-gates`

This generates stable outputs under `Visualizations/output/`:
- Allocation action lists: `allocations_thesis_manual_match_physical.csv`, `allocations_thesis_manual_match_coverage.csv`
- Schedules with start/end timestamps: `schedule_thesis_manual_match_physical.csv`, `schedule_thesis_manual_match_coverage.csv`
- Evaluation summaries: `eval_thesis_manual_match_physical.txt`, `eval_thesis_manual_match_coverage.txt`
- Thesis figures (Gantt): `gantt_thesis_manual_match_physical.png`, `gantt_thesis_manual_match_coverage.png`
- A summary index: `thesis_demo_summary.txt`

The `--require-gates` option enforces thesis “good enough” feasibility gates for the strict run (non-zero exit on failure):
- overlaps = 0
- missing timestamps = 0
- laycan start violations = 0
- laycan end violations = 0

Evaluation metrics
------------------
The evaluation script reports:
- Actions served: number of allocated voyages.
- Overlaps: number of detected per-vessel overlaps in the exported schedule (after a small tolerance for timestamp noise).
- Missing times: count of missing start/end timestamps in the exported schedule.
- Laycan violations: count of voyages starting before laycan start or after laycan end.
- Manual overlap:
  * overlap on voyage id (how many manual voyages are served by the optimiser),
  * overlap with same vessel assignment (how many are served by the same vessel as in the manual plan).

Current results snapshot (thesis demo)
--------------------------------------
The following snapshot is taken directly from the generated evaluation artefacts.

1) Strict feasibility run (`eval_thesis_manual_match_physical.txt`)
- Status: Optimal (CBC, 60s time limit)
- Served voyages: 47 / 62
- Feasibility: overlaps=0, missing_times=0
- Laycan violations: start=0, end=0
- Manual overlap: 47 voyages overlap by id; 23 match the same vessel assignment

2) Coverage-first run (`eval_thesis_manual_match_coverage.txt`)
- Status: Optimal (CBC, 60s time limit)
- Served voyages: 52 / 62
- Feasibility: overlaps=0, missing_times=0
- Laycan end violations: 43 (starts after laycan end)
- Manual overlap: 52 voyages overlap by id; 23 match the same vessel assignment
- Configuration note: this run uses a soft laycan end (lateness penalised) to demonstrate the feasibility/coverage trade-off, not as a recommended operational policy.

Interpretation:
- The strict run is the thesis “physically realistic” baseline: it leaves voyages unserved when they cannot be started within the laycan constraints.
- The coverage-first run serves more voyages but does so by violating laycan end constraints, illustrating why explicit laycan semantics (hard vs soft) materially affects conclusions.
- This contrast is intentional: it motivates (a) why constraint semantics must be specified clearly, and (b) why “served count” alone is not a sufficient performance metric.

Limitations (explicit)
----------------------
This thesis-ready optimiser is intentionally limited:
- Laycan semantics are simplified and represented as start-time bounds only.
- Many business constraints are not modelled (cargo compatibility, vessel capability, port restrictions, open positions, contractual priorities, etc.).
- The objective is not a full profit/utility model; it is sufficient to demonstrate feasibility/coverage trade-offs on the sample scenario.
- Performance is demonstrated on the sample scenario and a manual subset; additional work is required for production-scale instances.
- The ML models are baselines: they are adequate to provide time estimates for a scheduling prototype, but they are not presented as the final predictive models for production.

Next steps (post-thesis / business-ready direction)
--------------------------------------------------
- Clarify laycan semantics with domain owners and encode the correct interpretation (start-by vs arrive-by vs complete-by).
- Add missing constraints required for real scheduling decisions (capability/compatibility, port restrictions, open positions, etc.).
- Establish performance guarantees (stronger pruning, decomposition, warm starts, solver settings, and heuristic fallbacks).
- Integrate with the operational system (API actions, targeted refresh, audit trail, permissions, and user-facing explanation).

Suggested thesis inclusions (recommended)
----------------------------------------
This subsection lists optional additions that typically strengthen the thesis narrative without expanding scope into “business-ready integration”.

1) Pipeline overview figure (one diagram)
- A block diagram showing:
  raw exports → feature engineering → ML artefacts → optimiser request → MIP solve → schedule/actions → evaluation artefacts.
- This helps the reader separate “prediction” from “optimisation” and understand how artefacts are produced reproducibly.

2) Units and semantics table (one page)
- A small table explicitly defining:
  * `HOURS_PER_NM` (hours/nm), `sailing_days` (days), `turnaround_days` (days),
  * `t[j]` meaning (start time of voyage j),
  * laycan meaning for this prototype (start-time window),
  * what is hard vs soft and what the slack represents.
- This reduces ambiguity and makes later evaluation claims easier to defend.

3) Runtime/complexity note (short paragraph)
- Mention that naive job→job arc enumeration is O(n²) in voyages, motivating arc pruning.
- Report solver and budget used for thesis runs (PuLP + CBC, 60s time limit) and note that pruning is an approximation.

4) Minimal empirical ablations (tiny table)
- Include one small table (2–4 rows) with served count and violation counts for:
  * strict vs coverage-first (already available),
  * time-order vs reposition arc selection,
  * ML time estimates vs constant-speed/constant-turnaround baseline (optional).
- Even a tiny table makes the “options” section evidence-based.

5) Failure modes + mitigations (one paragraph)
- Examples: missing laycans, sparse turnaround features, poor time estimates, infeasible instances, solver timeouts.
- Mitigations in this prototype: explicit laycan policy toggle, unserved option, bounded lateness (optional cap), arc pruning, and evaluation gates (`--require-gates`).

6) Validity caveats (explicit, short)
- Separate feasibility validity (no overlaps, time-window adherence) from optimality validity (objective is a proxy; constraints incomplete).
- State explicitly that this is a thesis prototype and that business constraints/integration are future work.
